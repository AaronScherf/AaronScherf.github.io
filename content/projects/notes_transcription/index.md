A cost-routed pipeline that turns short, unstructured academic PDFs — TA notes, problem sets, exams, and handwritten scans — into clean, LLM-ready Markdown, plus a downstream correction pass that catches the errors the routing itself can't see.

<!--more-->

Academic notes are a different problem from textbooks: no table of contents to anchor against, usually too short to need chapter-aware chunking, and frequently mixing typed and handwritten content on the same page — sometimes exported from apps (OneNote, Nebo, MyScript) whose internal page layout can split a single paragraph across a page boundary non-adjacently. `transcribe_notes.py` handles this with a three-tier router instead of always calling the API: a reliably-paginated, machine-generated document (LaTeX, Word) with clean local text gets extracted for free, zero API calls; if some of its pages are defective, only those pages are batched to Gemini for repair using the surrounding clean pages as context; and once a document's defect rate crosses a threshold, or it's a genuinely handwritten or messy export, it goes through full transcription instead — batched in one shot for reliably-paginated documents, or page-by-page with a small sliding window of already-transcribed pages as context for messy exports specifically, since resending the whole document on every call was confirmed to grow input tokens quadratically with page count on a real 25-page file. That routing decision leans conservative on purpose: OneNote's own local text extraction silently drops equation regions entirely rather than producing anything recognizably corrupted, so documents from known messy-export sources are routed straight to full transcription unconditionally rather than trusting a per-page cleanliness check that would confidently ship missing math with no warning. A cost comparison against dedicated OCR APIs (Mathpix, Mistral) confirmed the batching-plus-cheap-model design already beats their per-page rates, coming in around $0.0012–0.0013 per repaired page.

Getting a document routed to the right tier turned out not to be the whole story — the *quality* of that "free" local text mattered too. Two real problems surfaced on inspection. First, the choice of PDF text-extraction library mattered: `pypdf` was confirmed, across roughly 1,150 real pages spanning ten documents, to silently collapse spacing between words on some font/kerning setups ("LetVbe a finite-dimensional...") in a way `PyMuPDF`'s layout-aware extraction never did — swapping the library fixed it for free, with zero cases found where PyMuPDF did worse. Second: plain text has no way to represent a superscript or subscript at all, so `D^5` and `R^2` both silently come out as bare `D5`/`R2` — real content loss, not a bug either library could patch on its own. A regex proxy for that loss needed real tuning before it was trustworthy — an early, unanchored version matched embedded hyperlink hash IDs constantly, inflating one clean document's apparent defect rate from 0% to a spurious 50%, fixed by anchoring it to require the pattern stand alone between word boundaries. With that signal added and the defect threshold for triggering full-document repair dropped from 35% to 10% — real per-page Gemini cost turned out to be about seven-hundredths of a cent, so there was little reason to keep preserving free-but-flawed local text once a document had shown any real problem — the "too defective to patch page-by-page" fallback was rebuilt to batch the entire document through Gemini in a handful of calls. Run for real against a 43-page problem set: a 63% combined defect rate correctly triggered the new path, all batched calls succeeded on the first try, and the whole document was cleanly re-transcribed with correct LaTeX throughout for about two cents.

That still left something on the table: a follow-up look at PyMuPDF's structured text mode — which exposes each character span's font size and vertical position, not just its text — showed the same information needed to *recover* a lost superscript or subscript locally, for free, rather than only detecting its absence. A real span-level check (smaller than the line's dominant size, and vertically offset from its baseline, since size alone isn't a reliable signal) recovers the large majority of them, validated against real ground truth already sitting on hand — two documents whose pages had already been correctly transcribed by Gemini before this feature existed — where every sub/superscript checked across 13 real pages matched, from simple cases like `D^5` and `x^2` to compound ones like `H_f(x)` and nested set notation. The practical effect was substantial: one 43-page problem set's defect ratio dropped from 63% back down to 5%, correctly returning it to targeted 2-page repair instead of a 43-page rewrite, and a second document dropped from a hypothetical 73% to 9%. A related bug surfaced during this same structured-mode work: PyMuPDF reconstructs each line by concatenating its character spans directly, but that reconstruction never checked the *positional* gap between two spans — a common LaTeX/PDF pattern uses pure kerning-level horizontal offsets for a word boundary instead of an explicit space character, so text like "that 𝑓 uniformly" was silently coming out "that𝑓uniformly" with no error of any kind to flag. A gap-based synthetic-space threshold, tuned against the real span data, fixed it — confirmed directly on the motivating page, and it also measurably reduced how defective the affected 155-page document scored (36 defective pages down to 21) before that document was fully re-transcribed through Gemini anyway once its remaining defect rate still cleared the 10% threshold.

A full page-by-page audit of the sub/superscript recovery work turned up one more, narrower case: a square-root sign that silently extracts as an ordinary ASCII letter `p` — invisible to every defect check built so far, because it doesn't look wrong, just different. That specific finding is what motivated a second, sibling tool: `postprocess_notes.py`, a downstream correction pass over already-produced Markdown rather than one more bespoke detection heuristic layered onto extraction. It targets local-only pages — the ones that never reached a vision model in the first place — using a free structural pre-filter (an isolated single letter standing alone on its own line, the exact shape of the confirmed real bug) alongside a layered statistical check built on local, CPU-only Hugging Face `transformers` models: a cheap causal-LM pass (GPT-2) narrows candidate positions by surprisal, and only that narrowed set gets a more expensive bidirectional masked-LM confirmation pass (DistilBERT), since a design spike found masked scoring produced by far the cleanest separation — the disambiguating evidence for the real bug sat *after* the error in the text, which only a model that reads both directions can use at all. Nothing gets corrected on a model's self-reported confidence alone: every surviving candidate is re-checked against its actual source PDF page image, reusing the same repair machinery already validated for the routing tiers above, so a fix is only ever applied once it's been verified against the real source. Run for real against the document that motivated it, it found and correctly fixed the actual bug (`page 6` now reads `$$\sqrt{h^2 + k^2}$$`, re-verified against the source image) while independently re-checking nine other flagged candidates and correctly leaving all of them untouched — ten real verification calls total, for well under a cent.

Testing that pipeline at real corpus scale — a 155-page lecture-note file plus two others — surfaced both a real bug and a real limitation. Dozens of pages were being flagged as suspicious, and every single flagged word turned out to be genuinely correct, just glued directly onto a math variable with no space — exactly the reconstruction gap described above, since this corpus predated that fix. Regenerating the corpus with the fix in place cut the number of genuinely defective pages substantially, though it also meant the document's remaining defect rate still crossed the whole-document-batching threshold on its own, so the post-processing test ended up validating fully-Gemini-transcribed text's precision rather than the extraction fix directly. Isolating the fix's effect required a second, still locally-extracted document, which surfaced a separate finding: the causal-LM layer flags a real, substantial fraction of correct words in terse, LaTeX-heavy problem-set prose — "subject," "compact," "explicitly" — simply because that register reads as statistically unusual to a general-purpose language model, independent of whether anything is actually wrong. Dumping the raw score distribution showed no clean cutoff fully separates that noise from genuine anomalies, but a data-driven threshold increase still cut real false-positive volume by roughly 62% without losing the signal the layer exists to catch. Source-image verification means this precision gap isn't a correctness risk — a false positive gets caught before any bad edit is made — just a real, currently-open cost-efficiency question for a future pass.

Both pipelines write the same kind of self-describing output: a YAML frontmatter block recording how each document was produced (routing tier, model used, pages repaired) ahead of the Markdown body, so a downstream indexer can filter or weight documents by provenance without re-deriving it from content. Together with the textbook side of the pipeline, described separately in **[Marker PDF Conversion](/projects/marker_conversion/)**, this feeds **Academic Hub**, a broader project that synthesizes textbooks, lecture notes, problem sets, exams, journal articles, and original research into a unified knowledge network powering AI assistants tuned to specific academic domains.
