A cost-optimized pipeline that turns dense, math-heavy textbooks into clean, LLM-ready Markdown using the open-source Marker model on rented GPU time — one half of a two-tool system that also handles short academic notes with a separate, GPU-free sibling (see **[Notes Transcription Pipeline](/projects/academic-hub/notes_transcription/)**).

<!--more-->

A small local tool drives the textbook side of the pipeline: it spins up a GPU virtual machine in Google Cloud, uploads every PDF found in a given course's folder — batch composition follows the folder, not a hand-maintained filename list, so pointing the same tool at a different course directory is the only change needed to run it against a new course — and converts them all in one pass with the open-source Marker model, reusing the same loaded model across every book to keep runtime and cost down. An optional AI-assisted step reads each book's title page to automatically label the output files with the correct title, author, and year, and the converted Markdown and extracted images are copied back locally before the VM and its disk are torn down entirely: a Persistent Disk bills for its full size for as long as it exists, running or not, so for a pipeline used in occasional batches rather than continuously, deleting outright (and cheaply recreating it next time) beats paying to keep an idle disk around between runs.

That automation turned out to be more fragile than reproducible: its provisioning script pins OS-level dependencies for repeatability, but the Deep Learning VM image it boots from floats to whatever Google most recently publishes under that image family rather than staying fixed. A new image build shipped a newer NVIDIA Container Toolkit preinstalled than the script's pinned version expected, and apt refuses to downgrade an already-installed package to satisfy an exact-version dependency — provisioning failed outright with a cryptic "held broken packages" error, reproduced cleanly on a second from-scratch VM to rule out one-off disk corruption before trusting the diagnosis. The fix wasn't another pin, since that just delays the same break until the next image update (plausibly every few weeks); the toolkit install now resolves unpinned instead, so apt upgrades the preinstalled version to match automatically rather than conflicting with it, self-healing against whatever image build shows up next instead of needing a manual version bump on a recurring basis.

That pipeline used to split every book into fixed 150-page chunks with no awareness of what was at the boundary — a cut could silently land mid-table or mid-formula, and there was no way to resolve an author's own "see page 157" cross-reference against the converted text. It's since been rebuilt around a chapter-index abstraction, sourced from the PDF's embedded outline when it's genuinely chapter-granular or bootstrapped from the printed table of contents when it isn't, so chunk boundaries align to real chapter breaks instead of a fixed page count; any span that still can't be chapter-aligned falls back to a live safety probe that shifts the cut away from anything that looks like a mid-table or mid-formula split. Every page also gets tagged with both its physical PDF page number and, where derivable, the book's own printed folio number. Validated across four structurally different books (born-digital with real links, born-digital with a table-style table of contents, and fully scanned with no embedded structure at all): zero duplicate internal anchors — a real bug in the old chunked output — and 96–98% folio-tag coverage once the three separate root causes behind an initial 0% run were tracked down and fixed.

A second script, `describe_images.py`, runs as a follow-on pass over whatever `convert_textbook.py` already produced — no GPU, no VM, just local files and a Gemini API call, so it's a cheap post-processing step rather than more time on rented hardware. Deciding which of a book's extracted images are worth describing at all is split into two stages: a free filter first drops anything on or before the book's last front-matter page (cover art, publisher logos, title-page decoration) using the chapter boundary the chunking work above already computes, at zero API cost; every image that survives gets one combined Gemini call that both decides whether it's decorative and, if not, writes the description in the same pass. Each description is inserted as a blockquote directly beneath its image link in a derived `.rag.md` file — strictly additive, so the original converted Markdown is never touched — and every result is cached to disk as soon as it's produced, so a rate-limited or interrupted run resumes without re-billing images it already described. Building this surfaced a real, pre-existing bug in every book converted so far: Marker saves each image under a `pg_{page}_{img_key}` filename, but the Markdown it writes links to the bare, chunk-local `img_key` instead — every single image link in every previously-converted book was silently broken, confirmed directly against real output where nothing in the Markdown matched a file on disk. Fixed with a remap applied at the moment each image is saved, since `img_key` alone isn't even unique once a book spans multiple chunks. Run for real across five books, it described 764 of 793 candidate images and correctly skipped the other 29 as decorative — Axler (31/36), Hammack (124/132), Rudin (2/5), Simon (199/204), and Sydsæter (408/416) — and spot-checks across three of those books turned up genuinely specific descriptions (a position-vector diagram, a cobweb diagram, a Brouwer fixed-point setup, a number line correctly told apart from a decorative line drawing it skipped), not generic hand-waving.

Textbooks are the easy case for this kind of pipeline in one specific sense: they're long, but they're *structured* — reliably paginated, printed text, with a table of contents to anchor against. Academic notes are the opposite problem: TA lecture notes, problem sets, exams, and handwritten scans have no table of contents, are usually too short to need chapter-aware chunking at all, and frequently mix typed and handwritten content on the same page. None of this pipeline's chunking or page-tracking machinery applies there, so that side of the project is a separate, GPU-free sibling script with its own cost-routing logic and its own downstream error-correction pass, covered in **[Notes Transcription Pipeline](/projects/academic-hub/notes_transcription/)**.

This pipeline and its sibling write the same kind of self-describing output: a YAML frontmatter block recording how each document was produced ahead of the Markdown body, so a downstream indexer can filter or weight documents by provenance without re-deriving it from content. Together they feed **Academic Hub**, a broader project that synthesizes textbooks, lecture notes, problem sets, exams, journal articles, and original research into a unified knowledge network powering AI assistants tuned to specific academic domains. The same split — a heavyweight, structure-aware tool for large well-formed documents and a lightweight, vision-first tool for short and messy ones — generalizes to any dense, mixed-format PDF archive that needs to become queryable by an LLM or RAG system.

Running this pipeline unattended, across many courses, surfaced a genuinely different class of problem than the content bugs above: a course's reading list often overlaps with another course's, and reconverting the same book twice wastes rented GPU time for no benefit. A duplicate check now runs before any VM is even created — free, local, and offline — matching an incoming PDF against every book already converted anywhere in the corpus, first by exact byte hash and then by fuzzy title/author/year. A high-confidence fuzzy match (above 0.85 similarity) is skipped immediately rather than blocking on a person to confirm it first, on the reasoning that the two mistakes aren't equally costly: wrongly skipping a genuinely new book only costs a follow-up conversion once it's noticed, while wrongly reconverting a real duplicate burns real GPU-hours that are gone either way — so it's logged to a small review queue instead, checkable at any later, convenient time. That reuse mechanism itself surfaced a real bug: a book skipped this way is recorded with a derived identity rather than a hash of its own bytes, and a later reindex of its course could silently evict the *original* book's own catalog entry, confirmed live. Fixed at the root by having the reindex step recognize a skipped book's derived identity and leave it alone instead of colliding with the original.

The other piece of unattended operation is recovering when a book turns out to be too large for the VM's memory rather than stopping the whole batch to ask a person. Books are now queued largest-last, so a failure lands with as little of the batch left to affect as possible, and a memory failure now escalates automatically: reset and retry on the same machine first, move up to a larger machine if the same book fails again on a fresh attempt, and only interrupt a person if the larger machine fails too — each step first confirming, from the VM's own kernel log, that the failure really was memory pressure and not something else entirely. An early version of this escalation had a subtle problem of its own: recovering from a failure necessarily involves wiping and relaunching, which was also wiping the very evidence the next escalation step needed to know it had already tried the smaller machine — closed by having each step save what it needs before touching anything.
