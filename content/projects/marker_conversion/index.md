A cost-optimized document pipeline that turns raw academic PDFs — from dense, math-heavy textbooks to short, often handwritten problem sets — into clean, LLM-ready Markdown, using two purpose-built tools instead of one one-size-fits-all OCR pass.

<!--more-->

A small local tool drives the textbook side of the pipeline: it spins up a GPU virtual machine in Google Cloud, uploads a batch of textbook PDFs, and converts them all in one pass with the open-source Marker model, reusing the same loaded model across every book to keep runtime and cost down. An optional AI-assisted step reads each book's title page to automatically label the output files with the correct title, author, and year, and the converted Markdown and extracted images are copied back locally before the VM shuts itself down to avoid idle billing.

That pipeline used to split every book into fixed 150-page chunks with no awareness of what was at the boundary — a cut could silently land mid-table or mid-formula, and there was no way to resolve an author's own "see page 157" cross-reference against the converted text. It's since been rebuilt around a chapter-index abstraction, sourced from the PDF's embedded outline when it's genuinely chapter-granular or bootstrapped from the printed table of contents when it isn't, so chunk boundaries align to real chapter breaks instead of a fixed page count; any span that still can't be chapter-aligned falls back to a live safety probe that shifts the cut away from anything that looks like a mid-table or mid-formula split. Every page also gets tagged with both its physical PDF page number and, where derivable, the book's own printed folio number. Validated across four structurally different books (born-digital with real links, born-digital with a table-style table of contents, and fully scanned with no embedded structure at all): zero duplicate internal anchors — a real bug in the old chunked output — and 96–98% folio-tag coverage once the three separate root causes behind an initial 0% run were tracked down and fixed.

A second script, `describe_images.py`, runs as a follow-on pass over whatever `convert_textbook.py` already produced — no GPU, no VM, just local files and a Gemini API call, so it's a cheap post-processing step rather than more time on rented hardware. Deciding which of a book's extracted images are worth describing at all is split into two stages: a free filter first drops anything on or before the book's last front-matter page (cover art, publisher logos, title-page decoration) using the chapter boundary the chunking work above already computes, at zero API cost; every image that survives gets one combined Gemini call that both decides whether it's decorative and, if not, writes the description in the same pass. Each description is inserted as a blockquote directly beneath its image link in a derived `.rag.md` file — strictly additive, so the original converted Markdown is never touched — and every result is cached to disk as soon as it's produced, so a rate-limited or interrupted run resumes without re-billing images it already described. Building this surfaced a real, pre-existing bug in every book converted so far: Marker saves each image under a `pg_{page}_{img_key}` filename, but the Markdown it writes links to the bare, chunk-local `img_key` instead — every single image link in every previously-converted book was silently broken, confirmed directly against real output where nothing in the Markdown matched a file on disk. Fixed with a remap applied at the moment each image is saved, since `img_key` alone isn't even unique once a book spans multiple chunks. Run for real across five books, it described 764 of 793 candidate images and correctly skipped the other 29 as decorative — Axler (31/36), Hammack (124/132), Rudin (2/5), Simon (199/204), and Sydsæter (408/416) — and spot-checks across three of those books turned up genuinely specific descriptions (a position-vector diagram, a cobweb diagram, a Brouwer fixed-point setup, a number line correctly told apart from a decorative line drawing it skipped), not generic hand-waving.

Textbooks are the easy case for this kind of pipeline in one specific sense: they're long, but they're *structured* — reliably paginated, printed text, with a table of contents to anchor against. Academic notes are the opposite problem. TA lecture notes, problem sets, exams, and handwritten scans have no table of contents, are usually too short to need chapter-aware chunking at all, and frequently mix typed and handwritten content on the same page — sometimes exported from apps (OneNote, Nebo, MyScript) whose internal page layout can split a single paragraph across a page boundary non-adjacently. None of the textbook pipeline's chunking or page-tracking machinery applies here, so it's handled by a separate, GPU-free sibling script, `transcribe_notes.py`, that renders each page to an image and asks a vision-capable Gemini model to transcribe whatever's actually on it, typed or handwritten, with no pre-classification required.

Rather than always calling the API, `transcribe_notes.py` routes each document to the cheapest tier its actual content supports. A reliably-paginated, machine-generated document (LaTeX, Word) with clean local text gets extracted for free, zero API calls. If some of its pages are corrupted — usually a broken font encoding on a big matrix bracket or summation sign, or collapsed word spacing — only those pages are batched to Gemini for repair, using the surrounding clean pages as context; on real 155- and 112-page files this repaired 36 and 31 pages respectively, both at a 100% first-try batch success rate with zero individual-page fallbacks needed. Everything else — genuinely handwritten or messy-export documents — goes through full page-by-page transcription with a small sliding window of already-transcribed pages as context, rather than the whole document: resending everything on every call was confirmed to grow input tokens quadratically with page count on a real file, while a 3-page trailing window preserves the same paragraph-continuity handling at flat, linear cost. That routing decision leans conservative on purpose: investigating whether handwritten exports could get the same free-tier treatment as textbooks turned up that OneNote's local text extraction *silently drops equation regions entirely* rather than producing anything recognizably corrupted, so a defect-detection heuristic built to catch garbled text would have shipped pages with whole equations missing and no warning. Documents from known messy-export sources are routed straight to full transcription unconditionally instead of trusting a per-page cleanliness check. A cost comparison against dedicated OCR APIs (Mathpix, Mistral) confirmed the batching-plus-cheap-model design already beats their per-page rates, coming in around $0.0012–0.0013 per repaired page.

Getting a document routed to the right tier turned out not to be the whole story — the *quality* of that "free" local text mattered too, once the goal became feeding these files to an LLM-based retrieval agent rather than just reading them. Two real problems surfaced on closer inspection. First, the library doing local text extraction mattered: `pypdf` was confirmed, across roughly 1,150 real pages spanning ten documents, to silently collapse spacing between words on some font/kerning setups ("LetVbe a finite-dimensional...") in a way `PyMuPDF`'s layout-aware extraction never did — swapping the extraction library fixed it for free, with zero cases found where `PyMuPDF` did worse. Second, and unfixable by choice of library: plain text has no way to represent a superscript or subscript at all, so `D^5` and `R^2` both silently come out as bare `D5`/`R2` — real content loss, not a bug either library could patch. A regex proxy for that loss needed real tuning before it was trustworthy: an early, unanchored version matched embedded hyperlink hash IDs constantly (`...app/06b7ab97dac5cbbb`), inflating one clean document's apparent defect rate from 0% to a spurious 50%; anchoring it to require the pattern stand alone between word boundaries fixed that false positive while still catching every real case. With that signal added and the defect threshold for triggering full document repair dropped from 35% to 10% — real per-page Gemini cost turned out to be about seven-hundredths of a cent, so there was little reason to keep preserving free-but-flawed local text once a document had shown any real problem — the "too defective to patch page-by-page" fallback was rebuilt to batch the *entire* document through Gemini in a handful of calls rather than loop one page at a time. Run for real against a 43-page problem set: a 63% combined defect rate correctly triggered the new path, all four batched calls succeeded on the first try, and the whole document was cleanly re-transcribed with correct LaTeX throughout for about two cents.

Detecting that loss and routing the whole document to Gemini worked, but it turned out to be leaving something on the table: a follow-up look at PyMuPDF's structured text mode (which exposes each character span's font size and vertical position, not just its text) showed the same information needed to *recover* a lost superscript or subscript locally, for free, rather than only detecting its absence. A real span-level check — smaller than the surrounding line's dominant size, and vertically offset from its baseline, since size alone isn't a reliable signal — recovers the large majority of them. Validated against real ground truth already sitting on hand (two documents whose pages had already been correctly transcribed by Gemini before this feature existed): every sub/superscript checked across 13 real pages matched, from simple cases like `D^5` and `x^2` to compound ones like `H_f(x)` and nested set notation. The practical effect was substantial — the 43-page problem set's defect ratio dropped from 63% back down to 5%, correctly returning it to targeted 2-page repair instead of a 43-page rewrite, and a second document dropped from a hypothetical 73% to 9%. Two honest limits stayed uncovered by design rather than chased down: recovering a fraction isn't possible this way, since a fraction is a two-dimensional stacked structure spanning multiple text lines rather than a same-line span issue, and a full page-by-page audit turned up one new, narrower case — a square-root sign that silently extracts as an ordinary letter, invisible to every defect check built so far because it doesn't look wrong, just different. That specific finding, more than any single bug, is what's steering the next phase of this project away from writing an ever-longer list of bespoke detection heuristics and toward a downstream correction pass instead.

Both pipelines write the same kind of self-describing output: a YAML frontmatter block recording how each document was produced (routing tier, model used, pages repaired) ahead of the Markdown body, so a downstream indexer can filter or weight documents by provenance without re-deriving it from content. Together they feed **Academic Hub**, a broader project that synthesizes textbooks, lecture notes, problem sets, exams, journal articles, and original research into a unified knowledge network powering AI assistants tuned to specific academic domains. The same split — a heavyweight, structure-aware tool for large well-formed documents and a lightweight, vision-first tool for short and messy ones — generalizes to any dense, mixed-format PDF archive that needs to become queryable by an LLM or RAG system.
